# Logging

- Status: active
- Scope: `Ryosuke-Shigi/codex-practice001`
- Last reviewed: 2026-06-10

## このドキュメントの目的

このドキュメントは、このプロジェクトにおけるログの分類、出力責務、保存先、記録項目、禁止事項を明文化するためのものです。

ログは、処理結果の確認、障害調査、外部API連携の追跡、運用上の判断に必要な事実を残すために使います。処理の正しさや業務判断そのものをログで代替しません。

## 基本方針

- ログには、処理開始・成功・失敗・対象件数・処理結果など、後から調査に必要な事実を残す
- ログ出力のために業務ロジックや責務境界を崩さない
- 同じ事実を複数レイヤーから重複して出力しすぎない
- 正常系で大量の詳細ログを常時出力しない
- ログ文言だけでなく、検索・集計しやすい context を付ける
- 未確認内容、推測、将来予定をログに残さない

## ログ分類と保存先

ログは用途ごとに Laravel の logging channel を分けます。

### sync

Job、Artisan Command、Schedulerなどによる同期処理の実行結果を記録します。

保存先の基本方針:

- `storage/logs/sync/` 配下の日次ログ
- `config/logging.php` のchannelは `daily` driver、`days` は14日を初期値とする

主な記録対象:

- 処理名
- 実行開始・終了
- 対象件数
- insert / update / skip / failed 件数
- 実行時間
- Job IDなどの追跡情報

### external_api

外部APIとの通信結果を記録します。

保存先の基本方針:

- `storage/logs/external-api/` 配下の日次ログ
- `config/logging.php` のchannelは `daily` driver、`days` は14日を初期値とする
- 外部APIごとに分離する必要が出た場合は、個別channelへの分割を検討する

主な記録対象:

- API名
- endpointを識別できる名前
- HTTP method
- status code
- request IDなど外部サービス側の追跡情報
- timeout、通信失敗、レスポンス不正

APIキー、Authorization header、秘密情報、レスポンス全文は記録しません。

### error

例外、処理失敗、部分失敗など、調査が必要な事実を記録します。

保存先の基本方針:

- Laravel標準のエラーログ、または本番監視対象のerror channel
- ファイル保存する場合は `daily` driver、`days` は30日を初期値とする
- 監視サービスを導入する場合も、秘密情報を送信しない

主な記録対象:

- 処理名
- 例外クラス
- エラーメッセージ
- 対象を特定するための安全なID
- 再実行可否の判断に必要な状態
- Job ID、request IDなどの追跡情報

同じ例外を複数レイヤーで重複記録しないようにします。

### operation

ユーザー操作や管理操作のうち、後から確認する必要がある重要な操作を記録します。

保存先は、目的に応じて次のように分けます。

- 一時的な調査・運用確認: `storage/logs/operation/` 配下の日次ログ
- ファイル保存する場合は `daily` driver、`days` は30日を初期値とする
- 監査履歴として検索・保持が必要: DBの監査テーブル

削除、重要な状態変更、管理操作、実行者・対象・変更前後の追跡が必要な操作は、ログファイルだけで済ませず、監査テーブルとして設計します。

主な記録対象:

- 操作名
- 操作者を特定するための内部ID
- 対象ID
- 実行結果
- 実行時刻

入力値全文や個人情報は記録しません。

## 保存先を分ける判断基準

保存先は、次の基準で決めます。

- 障害調査用であり、一定期間後に削除してよいものはログファイル
- 日次単位で確認する同期結果は専用のdaily channel
- 外部API通信は同期ログと分離し、通信障害を追跡しやすくする
- 重要操作の証跡として長期保持・検索・集計が必要なものはDB
- 本番監視対象の例外はerror channelへ出す

具体的なchannel名、ローテーション、監視連携は、実装対象が決まった時点でこのドキュメントへ追記します。

## 保持期間と自動削除

ログファイルと監査履歴は無期限保存にしません。保存先を決める時に、保持期間と削除方法も同時に決めます。

ログファイルの初期保持日数:

- `sync`: 14日
- `external_api`: 14日
- `error`: 30日
- 調査用の `operation`: 30日

ログファイルの基本方針:

- ファイル保存するchannelは原則として `daily` driverを使う
- `config/logging.php` の各channelに上記の `days` を必ず設定する
- 保持期間を過ぎたログファイルはLaravel / Monologのローテーションで自動削除する
- 一時調査のために保持期間を延ばした場合は、調査終了後に初期値へ戻す
- ログ量や障害調査期間から初期値が不適切と確認できた場合は、理由を記録したうえで変更する

DB監査履歴の基本方針:

- DB監査履歴の保持期間は、対象機能の法令・契約・業務要件ごとに決定する
- 保存期間の要件がある場合は、その期間を優先する
- 削除可能な監査履歴は、Schedulerから実行するArtisan Command / Jobなどで定期削除する
- 削除条件の決定はService、削除対象の取得・削除はRepositoryへ分離する
- 削除処理は件数、対象期間、成功・失敗をログへ記録する
- 削除してはいけない監査履歴を一括削除しないよう、保持区分や期限を明示する

## レイヤーごとの責務

### Job / Artisan Command / Scheduler

バックグラウンド処理や定期処理の実行単位を記録します。

- dispatchまたは実行開始
- 正常終了
- 失敗
- retryで追跡すべき情報

JobやArtisan Commandに業務判断を置かず、ログも実行境界の記録に限定します。

### Action

ユースケース全体の開始・終了・集計結果を記録します。

ServiceやRepositoryの内部処理を逐語的に重複記録しません。

### Service

業務上重要な判断結果や状態変化のうち、障害調査・運用確認に必要なものだけを記録します。

通常の条件分岐をすべてログへ出しません。

### Repository

Repositoryでは原則としてログを出しません。

RepositoryはDB操作または外部API境界に集中します。外部API通信の失敗をその場でしか取得できない場合は、例外へ必要な情報を付与し、上位レイヤーで記録できる形を優先します。

SQL、取得件数、保存値を無条件に大量出力しません。

### Controller / Request / Responder / Component

Controller、Request、Responder、React Componentでは、原則として業務ログを出しません。

HTTP入口、入力形式、出力整形、画面表示という各責務に限定します。アクセスログやフレームワーク標準の記録は、アプリケーションの業務ログとは分けて扱います。

## ログレベル

- `info`: 正常な処理開始・完了・集計結果
- `warning`: 処理継続は可能だが確認が必要な状態、部分失敗、skipの異常増加
- `error`: 処理失敗、例外、再実行や調査が必要な状態
- `debug`: ローカル調査用。常時必要な情報には使わず、本番での出力を前提にしない

ログレベルは、文言の強さではなく、運用上必要な対応の重さで決めます。

## contextの基本項目

必要な範囲で、次の項目をcontextとして付けます。

- `process`
- `action`
- `job_id`
- `request_id`
- `target_id`
- `result`
- `inserted_count`
- `updated_count`
- `skipped_count`
- `failed_count`
- `duration_ms`
- `exception`

すべての項目を毎回付ける必要はありません。処理の追跡と原因調査に必要な項目だけを使います。

## 記録しない情報

以下はログへ記録しません。

- `.env` の実値
- APIキー
- access token、refresh token
- Authorization header
- DBパスワード
- SSH情報、AWSキー
- Cookie、Session ID
- 個人情報
- 入力フォームやリクエストbodyの全文
- 外部APIレスポンスの全文
- 巨大payload、XML、JSON全文
- ファイル内容そのもの

調査に必要な場合でも、内部ID、件数、hash、status codeなど、秘密情報を含まない識別情報へ置き換えます。

## 例外時の基本項目

例外を記録する場合は、次の情報を必要な範囲で残します。

- どの処理で失敗したか
- どの対象で失敗したか
- 例外クラス
- エラーメッセージ
- Job IDまたはrequest ID
- 再実行時に対象を特定できる安全なID

例外を握りつぶしてログだけ残し、正常終了として扱いません。

## テスト方針

ログは補助情報であり、業務仕様そのものを固定する手段にはしません。

次の場合にログテストを検討します。

- 重要な失敗時にerrorログが必須
- 同期処理の完了件数を運用監視に使用する
- 秘密情報がcontextへ混入しないことを確認する必要がある
- 監査テーブルへの保存が業務要件である
- 保持期間を過ぎた監査履歴の定期削除が業務要件である

通常のinfoログ文言だけを固定するテストは増やしません。監査テーブルを実装する場合は、Repository、Service、Actionの責務を分離し、DB保存条件と削除条件をテストで固定します。

## 今後の更新方針

最初からすべてのchannelや監視連携を確定しません。

実際の機能へログを追加する時に、次の内容をこのドキュメントへ追記します。

- channel名
- 保存ファイル
- 初期保持日数から変更した場合の理由
- ローテーション設定
- 自動削除方法
- 監視対象
- 機能固有のcontext
- 監査テーブルの保存項目
- テスト対象

共通ルールを維持したまま、実装しながら必要な詳細を詰めていきます。
