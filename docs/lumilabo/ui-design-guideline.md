# LumiLabo UI設計方針

- Status: active

## 目的

LumiLaboのUIは、見た目の装飾性よりも、業務中に迷わず使えることを優先する。

年齢やIT慣れに関係なく、業務内容を理解していれば操作できるUIにする。読みやすい文字、押しやすいボタン、分かりやすい状態表示、迷わない導線を優先する。

画面ごとに自由なデザインを作らず、LumiLabo全体で統一されたUIにする。

## 正本方針

LumiLabo UI方針の正本は docs/lumilabo/ui-design-guideline.md とする。

PDF、画像、会話メモは視覚確認用の参考資料に留める。UIルールをPDFや画像だけに閉じ込めず、CodexAppが読む前提の判断基準はMarkdownへ落とす。

断定できない実装内容、未確認のファイル名、未確認のクラス名、実装済みでないUI部品を「既に存在する」と書かない。この文書はUI方針を固定するものであり、UI実装完了を意味しない。

## 案件詳細基準画面: Soft Industrial × Luminous UI

LumiLabo案件詳細は、今後のLumiLabo全体へ横展開する基準画面として `Soft Industrial × Luminous UI` を採用する。

Soft Industrial は、工房、作業台、設計設備、図面、薄い金属、制御パネルを連想させる面、枠、奥行きで表現する。ただし、重厚な工場設備、暗いサイバーパンク、過剰なガラス表現には寄せない。

Luminous UI は、LumiLabo固有のレモン色、薄黄色、短い光を、現在位置、編集中、保存中、保存完了、主要操作の理解に限定して使う。レモン色を全面へ塗らず、薄黄色の上に白文字を置かない。状態は色だけでなく日本語の文字で示す。

日本語UIでは、ボタン、説明、状態表示を原則として日本語にする。案件詳細から一覧へ戻る場合は `案件一覧へ戻る`、保存操作は `保存する`、保存中は `保存中です`、保存完了は `保存しました` とする。削除確認では `YES` / `NO` を使わず、`この案件を削除しますか？`、`削除する`、`削除しない` のように対象と結果が分かる文言を使う。

老眼を含む視認性では、会社名などの主見出しは28pxから36px相当、セクション見出しは20pxから24px相当、入力ラベル、入力内容、本文、ボタン文言、状態表示は18px以上、登録日などのメタ情報は16px以上を初期基準とする。画面に収めるために文字を小さくせず、改行、縦積み、領域拡張、フィールド内スクロール、レスポンシブ配置で調整する。主要ボタンと入力欄はモバイルで56px程度の高さを基準にする。

背景は、温かいアイボリーまたは薄いクリーム色を基本にし、低コントラストのグリッドや設計線で作業台や図面の雰囲気を出す。背景模様は情報より前へ出さず、常時動かさない。

案件詳細のフィールドは、入力欄1つずつを別カードにせず、意味のある作業領域としてまとめる。基本情報は会社名、担当者名、住所、メモ、表示専用の登録日を1つの作業領域に置く。地図は固定の地図風プレビュー自体をGoogle Maps検索URLへの導線とし、別タブで開く。地図の上へ操作文言を重ねない。写真は撮影操作と保存済み写真を分け、0件の場合は保存済み写真の見出し、枠、空領域を出さない。ファイルはクリックまたはタップで選択でき、PCでは複数ドラッグアンドドロップもできる文言にする。保存済みファイルも0件の場合は見出し、枠、空領域を出さない。

状態表示は、編集中、保存中です、保存しました、保存に失敗しましたに限定し、利用者へ知らせる必要がある時だけ日本語の文字で示す。未編集時は何も表示せず、状態表示専用の枠や空領域を作らない。色は補助として使い、保存中や保存完了の光は短く、操作結果の理解にだけ使う。ボタン押下は少し沈む程度にし、常時点滅や大きな移動、回転は使わない。非本質的な動きは動きを減らす設定を考慮する。

削除操作は通常操作や保存ボタンから距離を取り、赤系の色で示す。案件削除は確認ダイアログを通し、削除確定後も戻るボタンと同じ戻り先制御を使う。

レスポンシブは、モバイル縦、モバイル横、タブレット、PCの順に確認する。モバイルは1カラム、主要操作はfull width、横並びにしない。モバイル横はPC扱いにせず、文字サイズを下げない。タブレットはモバイルの操作順を維持し、必要な場合だけ2カラムへ広げる。PCは基本情報と、地図、写真、ファイルの作業領域を2カラム候補にしてよいが、工程詳細など別責務を追加しない。

今後TOP、選択、案件TOP、登録、一覧へ横展開する場合も、この基準を正本として、LumiLabo以外の画面、Backend、DB、API、S3へ影響させない。

## 画面導線

初期の画面入口候補は次を候補とする。

    LumiLabo Hub
      ↓
    案件システム
      ↓
    案件作成 / 案件一覧
      ↓
    案件詳細
      ↓
    工程詳細

案件詳細に工程詳細を詰め込まない。案件詳細では、案件基本情報と工程の状態把握を優先する。

工程詳細は、別画面または明確に分離された詳細領域として扱う。画面が広いPCでも、責務の違う情報を無理に1画面へ混ぜない。

## モバイルファースト方針

LumiLaboはモバイルファーストで設計する。最初にスマートフォン縦を基準にし、次にスマートフォン横、タブレット、PCを確認する。

スマートフォン横をPC扱いにしない。モバイルでは1カラムを基本にする。

主要操作は画面下部または操作エリア内に分かりやすく配置する。主要ボタンを左右横並びにしない。Primary Actionはfull widthを基本にする。複数の主要操作がある場合は縦積みにする。

## タブレット方針

タブレットはモバイル導線を崩さず、表示領域だけを広げる。

1カラムから2カラムへの拡張は許容する。ただし、案件詳細に工程詳細を雑に詰め込まない。

表示密度を上げる場合も、文字サイズを小さくして詰め込まない。

## PC方針

PCでは2カラムまたは3カラム表示を候補にしてよい。一覧と詳細の並列表示も候補にしてよい。

ただし、PCだからといって責務の違う情報を混ぜない。案件詳細と工程詳細は概念として分ける。

画面構造は共通にし、表示密度だけを拡張する。

## 1画面完結 / フィールド内スクロール方針

LumiLaboの画面は、原則として1画面内で主要操作が分かる構成にする。ページ全体を長くスクロールさせる設計に依存しない。

スクロールが必要な場合は、画面全体ではなく、一覧、詳細、説明、カード群などの専用フィールド内に overflow-y-auto を持たせる。

上部ナビゲーション、現在位置、主要操作、状態表示を見失わないようにする。

長文ドキュメントやログ全文など、読むこと自体が目的の画面では例外的に全体スクロールを許容してよい。

## 文字サイズ / 読みやすさ方針

モバイルでも文字が小さくなりすぎないことを重視する。画面内に情報を詰め込むために文字サイズを下げる設計は禁止する。

本文、入力内容、一覧の主要文字は16px相当以上を基本にする。補足説明、注釈、メタ情報は14px相当以上を基本にする。

重要な状態表示、ボタン文言、入力ラベルは小さくしない。薄いグレー文字を多用しない。

文字を小さくして情報量を増やすのではなく、表示項目、画面、詳細を分ける。

## 高齢ユーザーにも分かりやすいUI方針

LumiLaboは、高齢ユーザーやITに慣れていないユーザーにも分かりやすいUIを目指す。

アイコンだけの操作にしない。状態を色だけで表現しない。未実行、スルー、実行済などの文字を必ず表示する。

ボタン文言は短く、意味が分かる日本語にする。

- 案件を作成する
- 詳細を見る
- 一覧へ戻る
- 状態を変更する
- 保存する

エラー文は原因と次にすることが分かる文章にする。現在位置を見失わないよう、画面名とパンくずを表示する。

## ボタン / 操作方針

モバイルでは主要ボタンを左右横並びにしない。Primary Actionはfull widthを基本にする。

Secondary Actionは、full widthのoutline、本文内リンク、またはメニュー内操作にする。

保存、状態変更、削除、確定、送信などの重要操作を同一行に横並びさせない。

横並びボタンはPCまたは十分な横幅がある表示でのみ許可する。削除などの危険操作は、Primary Actionと近づけすぎない。

## 押下反応 / 画面切り替え / 動きの方針

ユーザーが押したことを分かりやすくする。ボタン押下時は、視覚的に押されたことが分かる反応を入れる。

- active状態
- pressed状態
- loading状態
- disabled状態
- 選択中状態

画面切り替え、タブ切り替え、詳細展開では、急に内容が入れ替わったように見えない動きを入れる。

ただし、過度なアニメーションや装飾的な動きは使わない。動きの目的は、見た目の派手さではなく、押した結果、現在位置、切り替わりを分かりやすくすることに置く。

状態変更や保存などの操作後は、成功、失敗、処理中が分かる表示を出す。モーションは短く、業務操作の邪魔にならない範囲にする。

## 色 / コントラスト方針

LumiLaboのブランド色はレモン色・薄黄色系を基本にする。

情報表示領域は白背景・黒文字を基本にする。レモン色や薄黄色の上に白文字など、低コントラストな文字を置かない。

色だけで状態を表現しない。ステータスBadgeには必ず文字を入れる。

強調には色を使ってよいが、読みやすさを優先する。

## 表 / グラフ / カレンダー方針

LumiLaboでは、業務状況を分かりやすくするために、表、グラフ、カレンダーを積極的に使う。ただし、情報を詰め込むために使わない。

表は、案件一覧、工程一覧、履歴、明細など、比較・確認に使う。

カレンダーは、予定日、期限、登録日、入金日、出金日、請求予定日などの把握に使う。

グラフは、件数、進捗、月別推移、状態割合など、全体傾向の把握に使う。

表、グラフ、カレンダーを同じ画面に常時すべて表示しない。モバイルでは、タブ、セクションボタン、表示モード切替で1つずつ表示する。

詳細な数値は、グラフだけでなく表や要約で補足する。

モバイルで横長テーブルをそのまま表示しない。列数が多い場合はカード型リストに変換する。表として表示する場合も重要列に絞る。

## 日付別カードカレンダー方針

LumiLaboのカレンダーは、月間カレンダーのマス目表示だけを前提にしない。

日付を縦に並べ、各日付の枠内に、その日に紐づくカードを表示する「日付別カードカレンダー」を基本候補とする。

横一列の日付表示ではなく、次のような日付ごとの縦並び表示を想定する。

    1日
    - 〇〇会社：120,000円
    - △△会社：80,000円

    2日
    - 表示なし

    3日
    - 案件A：元調予定
    - 案件B：見積提出

日付またはカードをクリックすると、下部または別領域に詳細を展開する。

カレンダー上で全詳細を完結させない。カレンダーは日付別の入口として扱う。詳細はカード詳細、案件詳細、工程詳細などへ分ける。

モバイルでは、ページ全体を長くスクロールさせず、カレンダー表示フィールド内でスクロールする。

入金カレンダー、出金カレンダー、請求カレンダー、案件カレンダー、工程カレンダー、横断カレンダーへ拡張できる構造を意識する。

## カードをswitchとして扱う方針

LumiLaboでは、案件、工程、入金、出金、請求などを、日付付きカードとして扱えるようにする。

カードは単なる表示部品ではなく、状態によって後続の表示、導線、完了判定、次工程の扱いが変わるswitchとして扱う。

工程カードの初期状態は次を基本とする。

- 未実行
- スルー
- 実行済

未実行は、対応が残っている状態。スルーは、この案件では不要として処理済みに近い扱い。実行済は、実際に対応した状態。

カード状態によって、カレンダー上の表示、案件詳細上の表示、次工程の強調、完了判定を変える。

ただし、この判断はReact Componentに直接持たせない。PRODUCT段階では、状態による判断はService / Presenterなどの境界で扱う。DTOは判断本体ではなく、確定済みの値を受け渡す境界として扱う。

UI側は、受け取った状態と表示用propsをもとに表示する。

## 画面別ルール

### 案件作成

会社名、担当者名、住所、メモを入力する。

登録日はユーザー入力にしない。作成日時 created_at の表示として扱う。

モバイルでは入力欄を縦積みにする。主要ボタンはfull widthにする。

### 案件一覧

案件の入口画面として扱う。

会社名、担当者名、ステータス、登録日、詳細導線を分かりやすく表示する。

モバイルではカード型リストを基本にする。PCでは表形式を候補にしてよい。

表示切替として、カード、表、カレンダー、グラフを将来候補にしてよい。ただし常時すべて表示しない。

### 案件詳細

案件基本情報と工程状態の見通しを優先する。工程詳細を詰め込まない。

工程はボタンと状態表示までに留める。見積、元調、請求、発注などの工程を分かりやすく並べる。

工程をクリックすると工程詳細へ進む。状態は色だけでなく文字で表示する。

### 工程詳細

予定日、メモ、状態、チェック項目などの詳細を表示する。

状態変更や保存などの主要操作はモバイルで横並びにしない。

状態変更は、押した結果が分かるようにする。

工程詳細の中でさらに情報が多くなる場合は、セクション分けやフィールド内スクロールを使う。

## Common UI と Feature UI の責務境界

Common UIには、複数機能で実際に使う業務非依存の表示・操作だけを置く。

Common UIへ入れてよいもの。

- Button
- Card
- Badge
- Tabs
- Dialog
- Sheet
- Input
- Textarea
- EmptyState
- ErrorState
- LoadingState

Common UIへ入れないもの。

- 固定データ
- 仮データ
- API通信
- DB操作
- 権限判断
- 状態遷移判断
- 業務ステータス解釈
- 機能固有URL生成

Feature UIには、LumiLabo固有の表示、操作、UI状態を置く。

Feature UI候補は次のような役割を想定する。ただし、ここに書いた名前は実装済みComponentの存在を示すものではない。

- ProjectCard
- ProjectListItem
- ProjectSummaryPanel
- ProcessStatusButton
- ProcessDetailPanel
- DateCardCalendar
- CalendarDayColumn
- CalendarItemCard

Feature UIにも、業務判断、API通信、DB都合、権限判断、状態変化の最終判断を押し込まない。

## Tailwind / UIライブラリ方針

CSS方針はTailwind CSSを軸にする。

UI部品補助としてshadcn/uiは候補にしてよい。ただし、この文書追加ではshadcn/uiを導入しない。

Button、Card、Badge、Tabs、Dialog、Sheet、Input、Textareaなどを将来導入候補にする。

Tailwind className を画面ごとに自由に散らしてデザインを作らない。共通する余白、角丸、影、背景、枠線、ボタン、バッジ、カードは、共通UI Componentまたは定義済み方針に寄せる。

MUIなどの完成済みデザインへ全面的に寄せる前提にはしない。

## Storybookの扱い

Storybookは、UI部品をアプリ本体から切り離して確認するための開発環境として将来候補にする。

正本はMarkdownであり、Storybookは実装されたUI部品の見本帳・確認場所として扱う。

この文書追加ではStorybookを導入しない。導入する場合は、Common UIと表示専用Feature UIに絞る。

API通信、DB保存、Service判断、Inertia通信をStorybookへ持ち込まない。

## 禁止事項

この文書追加では次を行わない。

- React Component作成
- Tailwind実装
- shadcn/ui導入
- Storybook導入
- Migration作成
- Model作成
- Controller作成
- Request作成
- Action作成
- Service作成
- Repository作成
- DTO作成
- Event作成
- Listener作成
- Job作成
- Scheduler作成
- API通信追加
- DB保存追加
- 本番反映
- npm install
- npm run build

LumiLabo UI方針として次を禁止する。

- モバイルで主要ボタンを左右横並びにする
- 小さい文字で情報を詰め込む
- 色だけで状態を表現する
- 案件詳細に工程詳細を詰め込む
- 工程タブや工程ボタンに業務判断を持たせる
- Componentへ完了判定や状態判断を押し込む
- カレンダー上に全詳細を詰め込む
- 横長テーブルをモバイルへそのまま表示する
- PDFや画像だけを正本にする
- UIライブラリを導入したことにして書く
- 実装していないComponentを存在するものとして書く
- DB / Migration / Backend実装へ進む
- Docker / 本番反映へ触る

## PR前確認

PR前に次を確認する。

- docs追加だけになっているか
- 実装ファイルを変更していないか
- UI方針がモバイルファーストになっているか
- 主要ボタン横並び禁止が明記されているか
- 文字サイズを小さくして詰め込まない方針が明記されているか
- 高齢ユーザーにも分かりやすいUI方針が明記されているか
- 押下反応 / 画面切り替え / 動きの目的が明記されているか
- 表 / グラフ / カレンダーの扱いが明記されているか
- 日付別カードカレンダーが、縦の日付別カード表示として正しく書かれているか
- カードをswitchとして扱う考え方が明記されているか
- 案件詳細と工程詳細を分ける方針が明記されているか
- Common UI と Feature UI の責務境界が明記されているか
- 未確認の実装済みComponent名を存在断定していないか
- DB / Migration / Backend / Docker / 本番反映へ踏み込んでいないか
