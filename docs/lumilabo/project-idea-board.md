# LumiLabo 案件作成 IDEA BOARD

- Status: active
- Scope: LumiLabo / 案件作成 IDEA BOARD
- Last reviewed: 2026-07-04
- Canonical source: この文書と `/lab/lumilabo-project-idea-board` のタブ構成

## 目的

LumiLaboの最初の実作業として、案件作成 IDEA BOARD をブラウザで確認できる状態にする。
LumiLaboは案件管理機能そのものではなく、上位プロダクト / 上位ドメインとして扱う。
最初のサブシステムを案件システムとし、今回の主対象は案件作成MOCKへ進む前の登録項目、考え方、表示方針の整理にする。

これはPRODUCT実装ではない。
MOCK、DB、Backend本実装、API通信、カレンダーは扱わない。

## 画面構成

IDEA BOARD画面は次の上位タブを必須にする。

1. 概要
2. TOP
3. 案件
4. Coding

初期表示は概要とする。
選んだタブの内容だけを表示し、全内容を1枚に縦並びで表示しない。

上位タブに次は作らない。

- 案件作成
- 案件一覧
- カレンダー

登録 / 一覧 / 詳細 は、案件タブ内のセクションとして扱う。
今回の主対象は登録セクションである。
一覧 / 詳細 は後続として見えるだけに留める。

## 概要

概要タブでは、案件作成IDEA BOARDの位置づけを示す。

- LumiLaboは上位プロダクト / 上位ドメインであること
- 最初のサブシステムが案件システムであること
- 今回作るものは案件作成IDEA BOARDであること
- 案件作成MOCKへ進む前に、項目、考え方、表示方針、未確定事項を確認すること
- MOCK / PRODUCT / DB実装ではないこと
- カレンダーはまだ扱わず、各カードが日付を持った後に検討すること

## TOP

TOPタブでは、LumiLabo Hubから案件システムへ入る親導線を最低限だけ示す。
TOPは完成画面MOCKではなく、案件システムへ入った直後の位置づけを示す。

TOPで主に示すもの:

- 案件作成へ進む入口
- LumiLabo Hubから案件システムへ入る位置づけ
- 案件一覧、案件詳細、工程が後続であること

TOPタブでは、案件詳細や工程デッキを作り込まない。

## 案件

案件タブでは、登録、一覧、詳細をセクションとして持つ。
案件タブをルート案内やページ遷移説明にしない。
基本導線セクションや、番号付き導線カードは置かない。

### 登録

登録セクションは今回の主対象である。
案件作成は、LumiLabo案件システムの最初の入力入口として扱う。

入力対象:

- 会社名
- 担当者名
- 住所
- メモ

表示対象:

- 登録日表示
- ステータス初期表示

会社名は、案件作成の主情報として扱う。
担当者名は、会社側の担当者として扱う。
住所はテキストのまま扱い、郵便番号 / 都道府県 / 市区町村へ勝手に分割しない。
メモは任意入力とし、業務補足を置く。

登録日表示は入力欄にしない。
将来PRODUCTでは `created_at` 表示相当として扱う。

ステータス初期表示は「進行中」候補として扱う。
今回のIDEA BOARDでは保存処理もステータス変更UIも作らない。
キャンセル / 失注は初期画面に細かく増やしすぎず、「進行中 / 完了 / 終了」の概念整理までに留める。

初期項目へ案件名を勝手に追加しない。
必要になった段階で相談する前提にする。

登録セクションへ混ぜないもの:

- 登録日入力
- 案件名
- 分割住所
- ステータス変更UI
- 保存処理
- 工程カード情報
- カレンダー情報
- 完了判定に関わる情報

入力フォーム風の見せ方をしても、保存可能フォームや案件作成MOCKとして扱わない。

### 一覧

一覧セクションは後続として扱う。
案件一覧上位タブは作らない。
固定データ付き一覧MOCK、検索、絞り込み、ソート、本実装は作らない。

登録後に、作成した案件を一覧で確認するという概念だけを置く。
後続の一覧画面では、1案件 = 1カードのモバイルファースト構想にする余地を示す。

一覧で表示する候補:

- 会社名
- 担当者名
- ステータス
- 登録日
- 住所の短い表示候補
- メモの有無または短いメモ表示候補

状態は色だけでなく「進行中」など文字で表示する方針にする。
詳細へ進む操作はアイコンだけにしない方針にする。
ただし今回、詳細画面への実遷移は作らない。

### 詳細

詳細セクションは後続として扱う。
今回、案件詳細画面は作らない。

詳細では将来、案件基本情報と工程デッキ / 工程カードへの入口を扱う予定であることだけ示す。
工程デッキ、工程カード、固定データMOCK、詳細UIの作り込みはしない。
工程カードの状態変更、完了判定、スルー判定は扱わない。

## Coding

Codingタブでは、IDEA BOARD段階での構成方針を整理する。

- React Componentは、タブ切り替えと選択中タブの表示だけを担当する
- 表示文言やカード内容は型付き静的データに分ける
- Page / Component / data の責務を分ける
- Componentに業務判断を置かない
- DB / Backend / API通信 / 保存処理を持たせない
- 完了判定や業務状態の判断はReact Componentへ置かず、将来Service側で扱う

将来PRODUCT化する場合の責務境界:

- Controller: HTTP入口
- Request: 入力形式バリデーション
- Action: 1ユースケースの手順
- Service: 業務判断、状態判断、完了判定
- Repository: DB境界
- DTO: レイヤー間データ
- Presenter / Responder: Inertia propsなど表示用整形

## 確認観点

- 上位タブが 概要 / TOP / 案件 / Coding であること
- 上位タブに 案件作成 / 案件一覧 / カレンダー がないこと
- 初期表示が概要であること
- 選んだタブだけが表示されること
- 登録 / 一覧 / 詳細 が案件タブ内セクションであること
- 今回の主対象が登録セクションであること
- 案件タブに基本導線や導線カードがないこと
- 会社名 / 担当者名 / 住所 / メモが入力対象であること
- 登録日表示 / ステータス初期表示が表示対象であること
- 登録日を入力欄にしていないこと
- 案件名を初期項目へ追加していないこと
- 住所を勝手に分割していないこと
- 固定データ付き一覧MOCKや入力フォームMOCKになっていないこと
- カレンダー、案件詳細、工程詳細を作り込んでいないこと
- DB / Migration / Backend本実装へ踏み込んでいないこと
