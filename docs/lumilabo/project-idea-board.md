# LumiLabo 案件システム IDEA BOARD

- Status: active
- Scope: LumiLabo / 案件システム IDEA BOARD
- Last reviewed: 2026-07-04
- Canonical source: この文書と `/lab/lumilabo-project-idea-board` のタブ構成

## 目的

LumiLaboの最初の実作業として、案件システム IDEA BOARD をブラウザで確認できる状態にする。
LumiLaboは案件管理機能そのものではなく、上位プロダクト / 上位ドメインとして扱う。
最初のサブシステムを案件システムとし、案件作成を最初の入力入口として扱う。

## 画面構成

IDEA BOARD画面は次のタブを必須にする。

1. TOP
2. 案件
3. 案件作成
4. 案件一覧
5. Coding

初期表示はTOPとする。
表示中タブの内容だけを表示し、全内容を1枚に縦並びで表示しない。

## TOP

TOPは「LumiLaboとは何か」だけを説明する欄ではない。
LumiLabo Hubから案件システムへ入った最初のTOP画面として、次の入口と現在位置を整理する。

TOPで見せるもの:

- 案件作成へ進む入口
- 案件一覧を見る入口
- 案件システムの現在位置
- 案件詳細、工程、別サブシステムへ広げる余白

TOPでは実画面MOCKを作らず、案件システムTOP画面の考え方をIDEA BOARDとして見せる。

## 案件

案件タブは、案件作成タブへ進む前に「案件とは何か」「案件システムで何を扱うか」を理解する場所にする。

案件タブで整理するもの:

- 案件システムの目的
- 案件を起点に業務工程へつなげる考え方
- 案件作成、案件一覧、案件詳細、工程デッキ / 工程カードへの流れ
- LumiLabo配下の最初のサブシステムであること

基本導線:

```text
LumiLabo Hub
  ↓
案件システムTOP
  ↓
案件作成
  ↓
案件一覧
  ↓
案件詳細
  ↓
工程デッキ / 工程カード
```

案件詳細や工程デッキ / 工程カードの実装・MOCKには進まない。

## 案件作成

案件作成タブは、単なる入力候補リストではなく、案件作成画面がどういうものかを見せる。
案件作成は、LumiLabo案件システムの最初の入力入口である。

入力させる候補:

- 会社名
- 担当者名
- 住所
- メモ

表示する候補:

- 登録日表示
- ステータス表示

登録日は入力欄にしない。
将来のPRODUCTでは `created_at` 表示相当として扱う。
ステータス初期表示は「進行中」候補として扱う。

入力させないもの:

- 登録日
- 案件名
- 郵便番号 / 都道府県 / 市区町村などへ分割した住所
- 工程カード情報
- カレンダー情報
- 完了判定に関わる情報

作成後は案件一覧へつながる。
入力フォーム風の見せ方をする場合でも、保存可能フォームや案件作成MOCKとして扱わない。

## 案件一覧

案件一覧タブは、後続の一覧画面がどういうものかを見せる場所にする。
案件作成後に、作成した案件をどう確認するかを整理する。

案件一覧で整理するもの:

- 作成した案件を確認する場所であること
- 会社名、担当者名、ステータス、登録日を表示候補にすること
- 案件詳細へ進む入口になること
- 案件詳細画面そのものは作らないこと

固定データMOCKや一覧画面の本実装にはしない。
詳細画面への実遷移は作らない。
工程詳細や工程デッキへ踏み込まない。

## Coding

Codingタブは、読んだMDや対象外の羅列だけを置く場所ではない。
IDEA BOARDをどう組むか、将来どう責務分離するかという仕組みを整理する。

Codingタブで整理するもの:

- タブ切り替えの構造
- 表示データの持ち方
- Page / Component / data の分け方
- React Componentはタブ切り替えと表示だけを担当すること
- DB / Backend / API通信 / 保存処理を持たないこと
- 将来PRODUCT化する場合の Controller / Request / Action / Service / Repository / DTO / Presenter の責務分離
- 完了判定や業務判断はReact Componentへ置かず、将来Service側で扱うこと

## カレンダー

カレンダーは扱わない。
カレンダータブ、カレンダーMOCK、日付別カードカレンダーは作らない。
カレンダーは、案件、工程、入金、出金、請求などの各カードが定義された後に扱う。
必要な場合でも「将来、各カードが日付を持った後に扱う」程度の短いメモに留める。

## 責務境界

IDEA BOARDは設計・構想整理のための表示であり、業務ロジックを持たせない。
React Componentに完了判定や業務判断を入れない。
Backend層は作らない。

将来PRODUCT化する場合は、Controller / Request / Action / Service / Repository / DTO / Presenter の責務分離を前提にする。
DTOは判断本体ではなく、確定済み値の受け渡し境界として扱う。
状態判断や完了判定は将来Service側で扱う。

## 確認観点

- 必須5タブがあること
- 初期表示がTOPであること
- 表示中タブだけが表示されること
- TOPが案件システムTOP画面構想になっていること
- 案件タブが案件システム概要になっていること
- 案件作成タブが案件作成画面の考え方になっていること
- 案件一覧タブが作成後の確認先としての一覧画面構想になっていること
- Codingタブがタブ構成、表示データ、責務分離、将来PRODUCT化の仕組みを説明していること
- 登録日を入力欄にしていないこと
- 案件名を初期項目へ追加していないこと
- 住所を勝手に分割していないこと
- カレンダー、案件詳細、工程詳細を作り込んでいないこと
- DB / Migration / Backend本実装へ踏み込んでいないこと
