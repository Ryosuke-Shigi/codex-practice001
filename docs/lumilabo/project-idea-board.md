# LumiLabo 案件システム IDEA BOARD

- Status: active
- Scope: LumiLabo / 案件システム IDEA BOARD
- Last reviewed: 2026-07-05
- Canonical source: この文書と `/lab/lumilabo-project-idea-board` のタブ構成

## 目的

LumiLaboの最初の実作業として、案件システム IDEA BOARD をブラウザで確認できる状態にする。
LumiLaboは案件管理機能そのものではなく、上位プロダクト / 上位ドメインとして扱う。
最初のサブシステムを案件システムとし、案件作成を最初の入力入口として扱う。

これはPRODUCT実装ではない。
MOCK、DB、Backend本実装、API通信、カレンダーは扱わない。
PR差分とこのMDだけで、次に案件作成MOCKへ進む方向性が分かる状態にする。

## 画面構成

IDEA BOARD画面は次の上位5タブを必須にする。

1. TOP
2. 案件
3. 案件作成
4. 案件一覧
5. Coding

初期表示はTOPとする。
選んだタブの内容だけを表示し、全内容を1枚に縦並びで表示しない。

上位タブから次を削除しない。

- 案件作成
- 案件一覧

上位タブにカレンダーは作らない。
カレンダーMOCK、日付別カードカレンダーも作らない。

## TOP

TOPは、LumiLabo Hubから案件システムへ入った最初のTOP画面構想として扱う。
案件システムへ入った直後に、次の入口と現在位置が分かるようにする。

TOPで見せるもの:

- 案件作成へ進む入口
- 案件一覧を見る入口
- 案件システムの現在位置
- 案件詳細、工程、別サブシステムへ広げる後続余白

TOPでは案件詳細や工程デッキを作り込まない。
TOPを長い導線説明だけにしない。
固定データ付き一覧MOCK、入力フォームMOCK、カレンダーは作らない。

## 案件

案件タブは「案件とは何か」「何を1案件として扱うか」「案件システムで何を扱うか」を見せる概要タブにする。
案件タブは導線を見せる場所ではない。

案件タブに置くもの:

- 案件とは何か
- 何を1案件として扱うか
- 案件システムで何を扱うか
- 案件が後続の工程デッキ / 工程カードの起点になること
- 案件作成 / 案件一覧 / 案件詳細がそれぞれ何を担当するか
- LumiLabo は上位プロダクトであり、案件システムは最初のサブシステムであること

1案件として扱う初期情報:

- 会社名
- 担当者名
- 住所
- メモ
- 登録日表示
- ステータス表示

案件名は初期項目へ追加しない。
登録日は入力欄ではなく、将来PRODUCTでは `created_at` 表示相当として扱う。
住所はテキストとして扱い、郵便番号 / 都道府県 / 市区町村へ勝手に分割しない。

案件ステータス初期案:

- 進行中
- 完了
- 終了

初期作成時は「進行中」候補である。
完了は必要な工程を通り切った状態である。
終了はキャンセル、失注、対象外など途中で閉じる状態である。
今回はステータス変更UIや完了判定を作らない。

案件タブに入れてはいけないもの:

- 旧ルート説明
- ルート案内
- TOPからどこへ進むかの説明だけ
- 番号付き案内カード
- 案件作成タブの内容の丸ごと吸収
- 案件一覧タブの内容の丸ごと吸収
- 案件詳細画面の作り込み
- 工程デッキ / 工程カードの作り込み
- カレンダー

## 案件作成

案件作成タブは維持する。
案件作成は、LumiLabo案件システムの最初の入力入口として扱う。
入力対象と表示対象を分けて整理する。

入力対象:

- 会社名
- 担当者名
- 住所
- メモ

表示対象:

- 登録日表示
- ステータス初期表示

会社名は案件作成の主情報として扱う。
担当者名は会社側の担当者として扱う。
住所はテキストのまま扱い、郵便番号 / 都道府県 / 市区町村へ勝手に分割しない。
メモは任意入力とし、業務補足を置く。

登録日表示は入力欄にしない。
将来PRODUCTでは `created_at` 表示相当として扱う。

ステータス初期表示は「進行中」候補として扱う。
今回のIDEA BOARDでは保存処理もステータス変更UIも作らない。

案件名は初期項目へ追加しない。
必要になった段階で相談する前提にする。

案件作成タブで混ぜないもの:

- 工程カード情報
- カレンダー情報
- 完了判定に関わる情報
- 保存処理
- ステータス変更UI

入力フォーム風の見せ方をする場合でも、保存可能フォームや案件作成MOCKとして扱わない。

## 案件一覧

案件一覧タブは維持する。
案件一覧タブを案件タブ内へまとめない。
案件一覧は、案件作成後に作成済み案件をどう確認するかを見せる場所にする。

一覧として1件の案件をどう見せるかを示す。
モバイルでは横長テーブルではなくカード型リストを基本にする。
1案件 = 1カードとして見せる構想にする。

1件の案件カードで見せる候補:

- 会社名を主表示にする
- 担当者名を副情報として見せる
- ステータスを副情報として見せる
- 登録日を副情報として見せる
- 住所の短い表示候補を持つ
- メモの有無または短いメモ表示候補を持つ

状態は色だけでなく「進行中」など文字で表示する。
詳細へ進む操作はアイコンだけにしない。
一覧は案件詳細へ進む入口になる。

ただし今回、詳細画面への実遷移や詳細画面実装はしない。
固定データ付き一覧MOCKは作らない。
検索 / 絞り込み / ソート実装は作らない。
DB取得はしない。

案件一覧タブに入れてはいけないもの:

- 抽象カードだけ
- 「詳細への入口です」だけの説明
- 固定データ付き一覧MOCK
- 検索 / 絞り込み / ソート実装
- 案件詳細画面
- 工程詳細
- 工程デッキ
- カレンダー
- DB取得

## Coding

Codingタブでは、IDEA BOARD段階での構成方針を整理する。

- React Componentは、タブ切り替えと選択中タブの表示だけを担当する
- 表示文言やカード内容は型付き静的データに分ける
- Page / Component / data の責務を分ける
- Componentに業務判断を置かない
- DB / Backend / API通信 / 保存処理を持たせない
- 完了判定や業務状態の判断はReact Componentへ置かず、将来Service側で扱う

将来PRODUCT化する場合の責務境界:

- Controller: HTTP入口
- Request: 入力形式バリデーション
- Action: 1ユースケースの手順
- Service: 業務判断、状態判断、完了判定
- Repository: DB境界
- DTO: レイヤー間データ
- Presenter / Responder: Inertia propsなど表示用整形

## 確認観点

- 上位タブが TOP / 案件 / 案件作成 / 案件一覧 / Coding であること
- 案件作成タブと案件一覧タブが削除されていないこと
- 初期表示がTOPであること
- 選んだタブだけが表示されること
- カレンダータブが存在しないこと
- 案件タブに旧ルート説明や番号付き案内カードがないこと
- 案件タブが案件とは何か、1案件として扱う情報、案件ステータス、工程デッキ / 工程カードの起点を示すこと
- 案件作成タブが会社名 / 担当者名 / 住所 / メモを入力対象として持つこと
- 案件作成タブが登録日表示 / ステータス初期表示を表示対象として持つこと
- 案件一覧タブが1案件 = 1カードのモバイルファースト構想を持つこと
- 案件一覧タブが会社名、担当者名、ステータス、登録日、住所短縮、メモ有無を表示候補として持つこと
- 登録日を入力欄にしていないこと
- 案件名を初期項目へ追加していないこと
- 住所を勝手に分割していないこと
- 固定データ付き一覧MOCKや入力フォームMOCKになっていないこと
- カレンダー、案件詳細、工程詳細を作り込んでいないこと
- DB / Migration / Backend本実装へ踏み込んでいないこと
