## このドキュメントの目的

このドキュメントは、通常コメント・PHPDoc・JSDocの共通ルールを定めます。

コメントは、初見の人が主要処理の目的・責務・判断理由・制約を追えるようにするために使います。処理変更、テスト、設計整理の代替にはしません。

## 基本方針

- 説明文は日本語で書く
- クラス名、関数名、変数名、型名、コマンド、ライブラリ名、API項目名、正式な技術用語は英語のまま書く
- `@param`、`@return`、`@throws` 等のタグは英語のまま使い、説明文は日本語で書く
- 目的、責務、判断理由、制約、処理順、変更時に守る条件を残す
- 型やシグネチャ、コードから明らかな内容を重複して書かない
- 単純処理へ形式的なコメントを追加しない
- 未確認内容、推測、将来予定を書かない
- 外部API仕様、エラー原文、英語であることが仕様の文字列を翻訳しない

## PHP

コメント追加を検討する対象:

- クラスの責務やレイヤー上の配置理由が分かりにくい
- 公開メソッドの目的、引数、返り値、例外がシグネチャだけでは分からない
- 業務判断、状態判断、DB境界、外部API境界を扱う
- Action / Service / Repository / Responder / DTOの責務を読み違えやすい
- Job / Event / Listener / Commandの処理順や再実行条件が重要

DTO / ListDTOにはデータキャリアとしての責務説明を置いてよいものとします。ただし、業務判断、DB操作、HTTPレスポンス生成、画面表示判断を正当化するコメントは書きません。

## TypeScript / React

コメント追加を検討する対象:

- Component / Hook / Utilityの責務が名前やpropsだけでは分かりにくい
- stateを分離している理由が重要
- UI操作とデータ取得の境界が重要
- 非同期処理の順序、古い結果の無効化、競合防止を扱う
- 外部ライブラリやブラウザAPIの制約に合わせた理由を残す必要がある

JSDocは、公開Utilityや複雑なHookなど、呼び出し側が責務・制約を知る必要がある場合に使います。propsの型から明らかな説明は重複しません。

## テスト

テストコメントは、何の仕様や境界を守るテストなのか補足するために使います。

- テスト名だけで意図が伝わる場合は追加しない
- 境界値、外部API失敗、非同期処理、Fake実装等、前提の理解が必要な箇所に絞る
- コメントで曖昧な期待値を正当化しない
- コメント追加だけでテスト不足を解消した扱いにしない

## 禁止

- コードと異なる古い説明を残す
- 責務違反や暫定実装をコメントで正当化する
- 秘密情報、接続情報、個人情報を書く
- 処理を1行ずつ言い換えるだけのコメントを大量に追加する
- コメントがあることを完成条件にする

## 見直し

実装変更時は、関連コメントが現在のコード・テスト・docsと一致しているか確認します。

古いコメントは現在の実装に合わせて修正するか、不要であれば整理します。判断に必要な仕様が不足している場合は推測せず、責務境界または機能固有docsを確認します。
