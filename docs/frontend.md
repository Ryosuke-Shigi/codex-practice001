## このドキュメントの目的

このドキュメントは、このプロジェクトの React / Inertia / TypeScript 側における、画面責務、Component分割、props、UI状態、レスポンシブ表示、演出の境界を明文化するためのものです。

バックエンドの ADR / レイヤード責務をフロントエンドで崩さず、モバイル・横置き・PCで破綻しない画面を作ることを目的とします。

UIの見た目、操作、共通Component、Common配置の詳細は `docs/ui.md` に従います。

## 基本方針

- フロントエンドは React / Inertia / TypeScript を前提とする
- UIはモバイルファーストで構成する
- PC表示を先に作って縮小するのではなく、スマートフォン幅で成立する構成から決める
- Component、props、UI状態、表示責務を分離する
- バックエンドの業務判断やDB操作をComponentへ持ち込まない
- 見た目の演出より、視認性、操作性、情報の優先順位を優先する
- AIに画面全体を丸投げせず、人間が画面構成、責務、成功条件を決める

## モバイルファースト

実装と確認は、次の順序を基本とします。

1. スマートフォン縦向き
2. スマートフォン横向き
3. タブレット
4. PC

各表示で、最低限以下を確認します。

- 横スクロールが意図せず発生しない
- 操作対象が画面外へ隠れない
- 固定要素が本文やボタンを覆わない
- 文字、カード、画像が潰れない
- タップ対象が重ならない
- 縦向きと横向きで操作不能にならない
- 1画面に収める仕様では、不要なページスクロールを発生させない

スマートフォン横向きはPC表示として扱わず、縦幅が小さい独立した表示条件として確認します。

## Component の責務

Component は、画面表示、ユーザー操作、画面内のUI状態を担当します。

Componentへ置いてよいもの:

- propsの表示
- タブ、モーダル、選択状態などのUI状態
- クリック、タップ、スワイプなどの画面操作
- 表示順、開閉、選択中の強調など、画面内だけで完結する処理
- 共通UI部品の組み立て

Componentへ置かないもの:

- DB取得・保存
- 外部API通信の業務判断
- 状態変更の可否判定
- ランキングや同期対象などの業務ルール
- Laravel側で確定すべき権限判断
- Inertia propsを作るためのバックエンド集約処理

画面表示に必要なデータ整形は、可能な範囲でResponder側で行い、Componentは受け取ったpropsを表示できる状態にします。

## Page と共通Component

Page Component は、ページ全体の構成と、そのページ固有のUI状態を担当します。

複数機能で実際に使う業務非依存の表示・操作は `Components/Common` へ分離します。

共通化の対象例:

- Card
- Button
- Field
- Modal
- Loading
- ページ間で共通するナビゲーション

見た目が似ているだけで目的や操作が異なるものを、無理に1つへ統合しません。共通化によってpropsや条件分岐が肥大化する場合は、用途別Componentとして分けます。

Commonへ入れる条件、入れてはいけない責務、共通UIの状態は `docs/ui.md` に従います。

## props の方針

- propsは、画面表示に必要な値だけを渡す
- DB Modelや不要な内部カラムをそのまま渡さない
- Inertia propsの形はResponderで整える
- TypeScriptの型を定義し、画面側で値の存在を推測しない
- propsから業務ルールを再構築しない
- URL生成や表示補助などの純粋処理は、必要に応じて共通Utilityへ分離する

バックエンドで確定できる表示用情報は、Laravel側で整えてから渡します。Component側で同じ業務判断を重複実装しません。

## UI状態と永続状態

UI状態は、画面内の表示・操作のための状態です。

例:

- 選択中のタブ
- モーダルの開閉
- 自動送りの開始・停止
- 現在表示しているカード位置
- ホバー・フォーカス・展開状態

DBへ保存する状態、複数画面や再読込後も維持すべき状態、業務上のステータスは、UI状態だけで完結させません。Laravel側のAction / Service / Repositoryを通じて扱います。

## Common・Feature・Effects の分離

共通UI、機能固有UI、背景・演出を分離します。

例:

```text
resources/js/
├── Components/
│   ├── Common/
│   ├── Effects/
│   └── <Feature>/
├── Layouts/
├── Pages/
└── theme/
```

- `Components/Common` は、複数機能で使う業務非依存のカード、ボタン、入力、モーダルなどを扱う
- `Components/<Feature>` は、機能固有の表示・操作を扱う
- `Components/Effects` は、背景、水面、波紋、パーティクル、光の軌跡などの演出を扱う
- `Layouts` は、ページ間で共通する配置と枠組みを扱う
- `Pages` は、ページ全体の組み立てとページ固有のUI状態を扱う
- `theme` は、共通の色、サイズ、UI定義を扱う

Common Componentは業務固有のDTO、状態遷移、API通信へ依存させません。Effects Componentは画面の業務データや保存処理へ依存させません。

## 背景エフェクトと演出

- 背景エフェクトは独立したComponentとして実装する
- UIカード、入力、検索、一覧より前面に出さない
- 常時激しく動く演出を避ける
- モバイルでの発熱、電池消費、描画負荷を確認する
- 重いエフェクトは必要に応じて遅延読み込みを検討する
- エフェクトの切り替えで、既存画面のレイアウトを変更しない
- クリック、タップ、スワイプなどの主要操作を妨げない

見た目を追加する場合も、既存の操作性を成功条件に含めます。

## ラフ画像と実装仕様

ラフ画像は、色味、背景の雰囲気、光、密度、余白感などの視覚的方向性を伝えるために使います。

ラフ画像を実装仕様として扱いません。

- ラフ画像: 見た目の参考
- 指示用まとめ: 実装仕様

背景ラフには、原則としてUI、文字、コード、説明パネル、ボタンを入れません。

CodexAppへ渡す場合は、背景だけのラフ画像と、変更対象・成功条件・失敗条件・実装しないことを記載した指示用まとめを分離して渡します。

画像内に偶然含まれたUIや文言を、そのまま実装対象へ追加しません。

## 入力とバリデーション

フロントエンドでは、入力ミスを早く伝えるために、必須、文字数、形式、選択漏れなどを検知します。

ただし、フロントエンドバリデーションは最終防衛線ではありません。

Laravel側ではFormRequest / Requestによるバックエンドバリデーションを必ず行います。

- フロントエンド: UX改善
- バックエンド: 安全性と整合性

同じ入力条件を扱う場合も、バックエンドの検証を省略しません。

## TypeScriptの関数宣言方針

名前を持つ主要処理と、内部コールバックの役割が読み分けられるように、関数宣言とアロー関数を使い分けます。

関数宣言を使う対象:

- Page Component
- 共通Component
- カスタムHook
- 共通Utilityなど、ファイル外から役割が分かる名前付き処理
- ファイル内でも、独立した責務を持ち、他の処理から再利用する名前付き関数

例:

```ts
export default function Welcome() {
    // Page Component
}

function shouldIgnoreSwipeTarget(target: EventTarget | null) {
    // 独立した判定処理
}
```

アロー関数を使う対象:

- `useEffect`、`map`、`filter` などへ渡すコールバック
- `onClick`、`onChange` などのイベントハンドラー
- ComponentやHook内部だけで使う短い処理
- クロージャとして外側のpropsやstateを参照する処理

例:

```ts
useEffect(() => {
    // 副作用処理
}, []);

const handleTouchStart = (event: TouchEvent) => {
    // Hook内部のイベント処理
};
```

同じ責務の処理で、関数宣言とアロー関数を理由なく混在させません。既存ファイルをこのルールだけのために一括変換せず、新規追加・対象ファイルの修正時に揃えます。

`this` の固定を目的としてアロー関数を選ぶ必要は、Reactの関数Componentでは原則ありません。宣言形式は、処理の責務と利用範囲で判断します。

## アクセシビリティと操作性

- ボタンとして操作する要素は、ボタンとして実装する
- キーボードフォーカスを失わせない
- 色だけに依存して状態を伝えない
- 画像には用途に応じた代替テキストを設定する
- モーダル表示中の操作対象を明確にする
- 自動送りや自動アニメーションには、停止できる操作を用意する

## テストと確認

フロントエンドのテスト方針は `docs/testing.md` に従います。

変更後は、少なくとも以下を確認します。

- TypeScriptの型エラーがない
- ビルドが成功する
- 対象画面がスマートフォン縦向きで成立する
- スマートフォン横向きで破綻しない
- PC表示で必要な情報量を表示できる
- クリック、タップ、スワイプが競合しない
- Inertia propsの型と実データが一致する
- 既存Componentの責務を崩していない
- 不要なAPI通信や再描画を増やしていない
- 背景エフェクトが操作や可読性を妨げていない

## 変更時の確認項目

- Page Componentへ業務判断を追加していないか
- ComponentへDB・外部API責務を持ち込んでいないか
- propsが過剰になっていないか
- Commonへ業務固有の条件分岐を入れていないか
- Feature ComponentとCommon Componentの責務が分かれているか
- Common・Feature・Effectsが分離されているか
- モバイル縦向きだけでなく横向きも確認したか
- ラフ画像に含まれる要素を勝手に実装していないか
- バックエンドバリデーションを省略していないか
- 既存操作と表示を壊していないか
