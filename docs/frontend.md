## このドキュメントの目的

このドキュメントは、React / Inertia / TypeScript側の画面責務、Component分割、props、UI状態、レスポンシブ表示、演出の境界を定めます。

UIの見た目、操作、Common配置の詳細は `docs/ui.md` に従います。

## 基本方針

- React / Inertia / TypeScriptを前提にする
- モバイルファーストで構成する
- Component、props、UI状態、表示責務を分離する
- バックエンドの業務判断、DB操作、権限判断をComponentへ持ち込まない
- 演出より視認性、操作性、情報の優先順位を優先する
- 人間が画面構成、責務、成功条件を決め、AIへ画面全体を丸投げしない

## モバイルファースト

確認順:

1. スマートフォン縦
2. スマートフォン横
3. タブレット
4. PC

最低限確認すること:

- 意図しない横スクロールがない
- 操作対象が画面外へ隠れない
- 固定要素が本文やButtonを覆わない
- 文字、Card、画像が潰れない
- タップ対象が重ならない
- 縦向きと横向きで操作不能にならない
- 1画面に収める仕様では不要なページスクロールがない

スマートフォン横向きはPC扱いにせず、縦幅が小さい独立条件として確認します。

## Page / Feature / Common

### Page Component

ページ全体の組み立てと、そのページ固有のUI状態を担当します。

### Feature Component

機能固有の表示、操作、画面内状態を担当します。

扱ってよいもの:

- propsの表示
- タブ、モーダル、選択状態
- クリック、タップ、スワイプ
- 表示順、開閉、選択中の強調
- Common Componentの組み立て

扱わないもの:

- DB取得・保存
- 外部API通信の業務判断
- 状態変更の可否判定
- ランキング、同期対象等の業務ルール
- Laravel側で確定すべき権限判断
- Inertia propsを作るためのバックエンド集約

### Common Component

複数機能で実際に使う業務非依存の表示・操作だけを扱います。

見た目が似ているだけで目的や操作が異なるものを無理に統合しません。Commonへ入れる条件は `docs/ui.md` に従います。

## props

- 画面表示に必要な値だけを渡す
- DB Modelや不要な内部カラムをそのまま渡さない
- Inertia propsはResponderで整える
- TypeScript型を定義し、値の存在を推測しない
- propsから業務ルールを再構築しない
- URL生成や表示補助等の純粋処理は必要に応じてUtilityへ分離する

バックエンドで確定できる表示用情報はLaravel側で整えてから渡し、Component側で同じ業務判断を重複実装しません。

## UI状態と永続状態

UI状態の例:

- 選択中のタブ
- Modalの開閉
- 自動送りの開始・停止
- 現在表示しているCard位置
- hover、focus、展開状態

DBへ保存する状態、再読込後も維持すべき状態、業務ステータスはUI状態だけで完結させず、Action / Service / Repositoryを通じて扱います。

## ディレクトリ境界

```text
resources/js/
├── Components/
│   ├── Common/
│   ├── Effects/
│   └── <Feature>/
├── Layouts/
├── Pages/
└── theme/
```

- `Components/Common`: 業務非依存の表示・操作
- `Components/<Feature>`: 機能固有の表示・操作
- `Components/Effects`: 背景、水面、波紋、パーティクル、光等
- `Layouts`: ページ間で共通する枠組み
- `Pages`: ページ全体の組み立て
- `theme`: 共通の色、サイズ、余白、角丸等

Commonは機能固有DTO、業務ステータス、API通信へ依存させません。Effectsは業務データや保存処理へ依存させません。

## 背景エフェクト

- 独立したComponentとして実装する
- Card、入力、検索、一覧より前面に出さない
- 常時激しく動く演出を避ける
- モバイルの発熱、電池消費、描画負荷を確認する
- 重い演出は必要に応じて遅延読み込みする
- 切り替えによって既存レイアウトを変更しない
- クリック、タップ、スワイプを妨げない

演出追加時も、既存操作と可読性を成功条件へ含めます。

## ラフ画像と実装仕様

- ラフ画像: 色味、光、密度、余白感等の見た目の参考
- 指示用まとめ: 変更対象、成功条件、失敗条件、実装しないことを固定する実装仕様

背景ラフには原則としてUI、文字、コード、説明パネル、Buttonを入れません。画像内に偶然含まれたUIや文言を実装対象へ追加しません。

## 入力とバリデーション

フロントエンドでは入力ミスを早く伝えるため、必須、文字数、形式、選択漏れ等を検知します。

ただし、フロントエンドは最終防衛線ではありません。Laravel側ではFormRequest / Requestによるバックエンドバリデーションを必ず行います。

- フロントエンド: UX改善
- バックエンド: 安全性と整合性

## TypeScriptの関数宣言

関数宣言を基本とする対象:

- Page Component
- Common Component
- カスタムHook
- 共通Utility
- 独立した責務を持つ名前付き関数

アロー関数を基本とする対象:

- `useEffect`、`map`、`filter` 等のコールバック
- `onClick`、`onChange` 等のイベントハンドラー
- Component / Hook内部だけで使う短い処理
- 外側のpropsやstateを参照するクロージャ

既存ファイルをこのルールだけのために一括変換せず、新規追加・対象修正時に揃えます。

## アクセシビリティ

- Buttonとして操作する要素はButtonとして実装する
- キーボードフォーカスを失わせない
- 色だけで状態を伝えない
- 画像に用途に応じた代替テキストを設定する
- Modal表示中の操作対象を明確にする
- 自動送り・自動アニメーションに停止操作を用意する

## テストと確認

共通テスト方針は `docs/testing.md` に従います。

変更後は次を確認します。

- TypeScript型エラーがない
- frontend buildが成功する
- モバイル縦・横・タブレット・PCで成立する
- クリック、タップ、スワイプが競合しない
- Inertia propsの型と実データが一致する
- Page / Feature / Common / Effectsの責務が混ざっていない
- 不要なAPI通信や再描画を増やしていない
- 背景エフェクトが操作や可読性を妨げていない
